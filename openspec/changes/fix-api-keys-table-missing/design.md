## Context

後端已經完成 API key 管理功能：

- `ent/schema/api_key.go` 定義了 `APIKey` entity。
- `ent/gen/` 已產生對應的 client、query、mutation、privacy rule。
- `internal/domain/apikeys/` 實作 CRUD endpoint。
- `internal/middleware/apiKeyStore.go` 的 `ApiKeyMiddleware` 會在 runtime 查詢 `api_keys` 表。

但 `database/goose/` 內沒有建立 `api_keys` 表的 migration，因此現有資料庫（包含開發機與測試容器）都缺少此表，導致 middleware 與 API endpoint 一碰到資料庫就回報 `relation "api_keys" does not exist`。

本變更的目標就是補上這條 migration。

## Goals / Non-Goals

**Goals:**
- 產生一條 Goose migration，建立 `api_keys` 表及其 index。
- 該 migration 必須與 `ent/schema/api_key.go` 的欄位、型別、index 完全一致。
- 執行 migration 後，API key 相關測試能夠通過。
- 文件化產生 migration 的步驟，方便未來新增類似修正。

**Non-Goals:**
- 不改變 API key 的業務邏輯或介面。
- 不調整舊版 JWT token generator。
- 不針對現有資料做 migration 轉換（此表為全新資料表，無舊資料）。

## Decisions

### 1. 使用 Atlas/Ent diff 產生 migration，而非手寫 SQL

**原因：**
- `ent/schema/api_key.go` 已經是單一真相來源，用 Atlas diff 可以確保 SQL 與 schema 完全一致，避免手寫錯誤。
- 專案本來就有 `database/migrate_goose/main.go` 與 `task db:migrate` 支援 Atlas → Goose 格式。
- 手寫雖然快，但欄位順序、JSON 型別、timestamp 預設值、index 名稱等細節容易出錯。

**替代方案：** 手寫 `CREATE TABLE api_keys` SQL。已排除，原因如上。

### 2. 不修改 schema，只新增 migration

**原因：**
- 目前問題是「有 schema、無 migration」，不是 schema 錯誤。修改 schema 會牽動 gen 檔案，反而擴大變更範圍。
- 保持 schema 不變，只補 migration，風險最低。

### 3. 使用現有 `task db:migrate -- create_api_keys_table` 命名慣例

**原因：**
- 與既有 migration 檔名風格一致（`YYYYMMDDHMMSS_<action>.sql`）。
- `task db:migrate` 會自動呼叫 Atlas 產生 Goose 格式檔案。

## Risks / Trade-offs

| 風險 | 影響 | 緩解 |
|---|---|---|
| Atlas diff 需要可連線的資料庫 | 開發環境若沒起 `infra`，會無法產生 migration | 執行前先用 `task infra:start` 啟動 Postgres；或在 Atlas diff 時指定 `--dev-url` |
| 生產環境已有同名 table（可能性低） | migration 會失敗 | 此專案目前無 `api_keys` 表，若有同名物件需人工介入 |
| 產生的 SQL 與現有 schema 預設值不一致 | 可能導致 ent 寫入失敗 | 產生後比對 `ent/gen/migrate/schema.go` 的 `APIKeysTable` 與 migration SQL |

## Migration 內容預覽

預計產生的 SQL 大致如下（實際以 Atlas diff 輸出為準）：

```sql
-- +goose Up
-- create "api_keys" table
CREATE TABLE "api_keys" (
  "id" bigint NOT NULL GENERATED BY DEFAULT AS IDENTITY,
  "created_at" timestamptz NOT NULL,
  "updated_at" timestamptz NOT NULL,
  "name" character varying NOT NULL,
  "key_hash" character varying NOT NULL,
  "key_prefix" character varying(8) NOT NULL,
  "scopes" jsonb NULL,
  "expires_at" timestamptz NULL,
  "is_active" boolean NOT NULL DEFAULT true,
  "created_by" bigint NULL,
  "last_used_at" timestamptz NULL,
  PRIMARY KEY ("id")
);

-- +goose Down
-- reverse: create "api_keys" table
DROP TABLE "api_keys";
```

> 實際欄位順序與型別以 Atlas diff 結果為準；產生後會與 `ent/schema/api_key.go` 及 `ent/gen/migrate/schema.go` 交叉驗證。

## Verification Plan

1. 在本地啟動 `task infra:start`。
2. 執行 `task db:migrate -- create_api_keys_table` 產生 migration。
3. 檢查產生的 SQL 是否包含 `api_keys` 表與正確的 index。
4. 執行 `task goose:up`（或啟動 server）讓 migration 生效。
5. 執行 `task tests:auth` 確認 `TestApiKey*` 測試通過。
6. 確認 `psql` 中 `
d api_keys` 顯示預期欄位。
